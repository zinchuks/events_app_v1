# Промпти для розробки Event Radar

Поклади MVP_PLAN.md у корінь робочого репозиторію. Спочатку запускай P0, потім етапи S1–S12. Звичайні етапи можна робити в тій самій сесії. Коли сесія перевантажена або змінюється напрям роботи, відкривай нову в тому ж репозиторії та використовуй промпт відновлення. Чужі незавершені зміни не перезаписувати.

Для цього вже створеного проєкту починати з P4, а не повторювати P0. Поточна точка відновлення — [docs/HANDOFF.md](docs/HANDOFF.md), історія змін — [docs/WORK_LOG.md](docs/WORK_LOG.md), статуси етапів — [docs/PROGRESS.md](docs/PROGRESS.md). Обов’язковий порядок оновлення цих файлів визначений у [AGENTS.md](AGENTS.md).

## P0 — Перший запуск: аудит і підготовка плану

```text
Ми створюємо міжнародний персональний радар подій для iOS та Android. Повні вимоги й критерії готовності записані в MVP_PLAN.md у цьому репозиторії.

Прочитай наявні AGENTS.md та MVP_PLAN.md. Виконай тільки S0: перевір репозиторії-кандидати, ліцензії, код, залежності та можливість запуску; обери одну мобільну основу й спосіб повторного використання процесу збору подій. Зафіксуй commit SHA перевірених основ. Не приймай README «production-ready» за доказ готовності.

Створи docs/REPO_AUDIT.md, docs/ARCHITECTURE.md, docs/SOURCES.md, docs/SETUP.md і docs/PROGRESS.md. У прогресі створи записи S0–S12 з фактичними статусами. Додай короткий кореневий AGENTS.md або обережно доповни наявний: де лежать вимоги, як читати прогрес, які команди перевірок реально працюють, що означає готовність.

Робочі припущення можна вибрати самостійно й записати з причинами. Якщо бракує доступу/ключа, зафіксуй конкретний блокер і продовжуй незалежну роботу. Не замінюй перевірку реальної інтеграції mock-результатом. Не починай S1 та наступні етапи в цій задачі.

Наприкінці повідом українською: вибрана основа, що реально перевірено, що залишається неперевіреним, конкретні передумови S1 і рекомендований наступний крок. Не обіцяй строків чи готовності без перевірок.
```

## P1 — Універсальний промпт на один етап

Замінити S1 на потрібний номер. Не треба переписувати всі вимоги в чат.

```text
Прочитай AGENTS.md, MVP_PLAN.md, docs/ARCHITECTURE.md та docs/PROGRESS.md. Виконай етап S1 до його критеріїв готовності. Спочатку перевір фактичний стан коду й передумови; не повторюй уже завершену роботу.

Самостійно виконай необхідні зміни, запусти відповідні перевірки та виправ знайдені помилки в межах цього етапу. Перевір diff. Не реалізуй наступні етапи, крім мінімальних залежностей поточного; такі відхилення коротко зафіксуй.

Онови docs/PROGRESS.md та setup/architecture, якщо змінилися факти. Познач verified тільки після виконаних критеріїв. Відсутній native build, ключ або зовнішній тест запиши як неперевірений/blocked; продовжуй доступні незалежні частини. Не вважай демо-дані доказом реальної інтеграції.

Наприкінці дай короткий звіт українською: результат для користувача, перевірки й їх результати, залишені блокери та 3–5 кроків ручної перевірки саме цього етапу. Збережи checkpoint роботи в git відповідно до правил репозиторію; не зачіпай unrelated зміни користувача й не роби push без завдання.
```

## P3 — Перевірка завершеного етапу

```text
Перевір реалізацію останнього етапу за MVP_PLAN.md й docs/PROGRESS.md. Переглянь код і фактичні результати перевірок. Шукай конкретні дефекти, регресії, порушення приватності, помилки дат/зон, дублікати й невідповідність заявленої готовності доказам.

Виправ дефекти в межах поточного етапу, перевір виправлення та онови прогрес. Не додавай функцій наступного етапу і не роби великий рефакторинг без конкретної потреби. Якщо native чи зовнішня перевірка недоступна, вкажи що саме потрібно виконати на пристрої або в сервісі. Звіт українською: знайдено → виправлено → перевірено → залишається.
```

## P4 — Продовження в новій сесії

```text
Продовжуємо цей репозиторій. Прочитай AGENTS.md, docs/HANDOFF.md, останні записи docs/WORK_LOG.md, docs/PROGRESS.md, MVP_PLAN.md та docs/ARCHITECTURE.md. Перевір git status --short і git log -5 --oneline. Зістав точку зупинки з фактичним кодом та останнім запитом користувача. Не починай проєкт заново й не перезаписуй чужі незавершені зміни.

Продовжуй із першої незавершеної дії в межах поточного замовлення. Перед змінами познач завдання in_progress у handoff і додай стартовий запис у журнал. Якщо користувач замовив інший напрям, запиши новий обсяг. Рекомендація в handoff сама по собі не дозволяє наступний етап чи S12. Якщо попередня частина blocked, не називай її завершеною; виконуй незалежні перевірки в дозволеному обсязі.

Після суттєвих частин роботи та перед завершенням онови HANDOFF.md, WORK_LOG.md і потрібні статуси PROGRESS.md: що змінено/в яких файлах, що реально перевірено, точний крок зупинки, блокери, перша наступна дія та стан Git. Не залишай точку відновлення лише в чаті. Наприкінці дай короткий звіт українською; push тільки після окремого явного підтвердження користувача.
```

## P5 — Керований пакет із кількох етапів

Використовувати після стабільного S3, коли попередні критерії перевірені. Це дозволяє давати більші задачі без втрати контрольних точок.

```text
Прочитай документи проєкту й виконай послідовно S4 та S5. Перед наступним етапом заверши доступні перевірки поточного й онови docs/PROGRESS.md. Самостійно виправляй помилки в межах цих етапів. Не переходь до S6. Якщо блокер унеможливлює залежну частину, залиш її blocked і виконай незалежні завдання. Звіт має відокремлювати implemented від verified.
```

## P6 — Фінальний аудит MVP

```text
Перевір весь MVP проти розділу «Визначення готового MVP» у MVP_PLAN.md. Простеж кожну вимогу до коду й фактичного тесту. Перевір iOS/Android, real sources, авторизацію/RLS, географію, переклади, DST/розклади, дублікати, restart/retries, push, покупки/restore/expiry та account deletion.

Створи docs/MVP_ACCEPTANCE.md зі статусом кожного критерію та доказами. Виправ підтверджені дефекти; не розширюй scope. Не називай продукт готовим, якщо ключові перевірки замінені mocks або не виконані. Окремо зазнач «готово до бети», «release builds готові» й фактичний статус публікації в магазинах.
```

## Шаблон короткого AGENTS.md

Це пропонований текст для власного кореня репозиторію. Наявні інструкції потрібно узгодити, а не затирати.

```markdown
# Project instructions

- Read MVP_PLAN.md and docs/PROGRESS.md before implementing a task. Read docs/ARCHITECTURE.md for cross-module changes.
- Implement the requested stage or explicitly requested stage range. Resolve routine implementation choices yourself and document significant decisions.
- Preserve the product requirements: iOS and Android; multiple territories including polygons; independent filters and notification schedules; translated descriptions with source attribution.
- Verify third-party code, licenses, source data permissions and APIs before relying on them. Preserve required attribution. Never invent integrations, event facts or test results.
- Keep secrets server-side; apply RLS to private data. Handle timezone/DST, idempotency and unknown values explicitly.
- Use clearly labelled fixtures in development. Real integrations and native checks remain unverified until actually exercised.
- Run relevant checks from docs/SETUP.md, inspect the diff, update progress with evidence. Add focused tests for core invariants and concrete risks.
- Record implemented, verified and blocked separately. A code commit is not proof of a store release or live delivery.
- Preserve unrelated user changes. Follow repository git conventions and never push or publish without task authorization.
- Communicate results and blockers in Ukrainian.
```

Ручні контрольні точки користувача: перший реальний наскрізний сценарій S3; правила й UX S4–S5; графіки/push S7–S8; sandbox purchases S9; бета S11. Це перевірки продукту, а не необхідність погоджувати кожне технічне рішення.
