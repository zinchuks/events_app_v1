# План розробки міжнародного радара подій

Версія 1.0 — 2026-10-01. Робоча назва: Event Radar; це не перевірений бренд.
Документ описує цільовий MVP, а не вже створений продукт. Усі етапи нижче спочатку мають статус pending.

## 1. Мета й спосіб роботи

Користувач налаштовує території, категорії, дати та мову. Сервіс збирає події з дозволених джерел, нормалізує їх, перекладає й надсилає персональні добірки за графіком. Застосунок обов'язково працює на iOS та Android.

Codex отримує весь цей документ одразу як контекст. Реалізація відбувається за етапами S0–S12. Одна задача може охоплювати один етап або явно визначений набір етапів. Codex сам виконує необхідні кроки й виправляє помилки всередині замовленого етапу. Не потрібні окремі промпти на кожен файл.

Перед роботою читати AGENTS.md, цей план і docs/PROGRESS.md. Після роботи оновлювати прогрес, фактичні команди перевірок і залишені блокери. Документи в репозиторії зберігають стан між сесіями; історія чату не є єдиним джерелом вимог.

## 2. Межі MVP

Обов'язково:
- iOS та Android зі спільною кодовою базою React Native / Expo / TypeScript.
- Ручний вибір кількох країн, регіонів і міст; радіус навколо точки; власний полігон, створений точками на карті.
- Кілька незалежних збережених правил; території всередині правила поєднуються через OR. Категорії — також OR. Різні групи фільтрів поєднуються через AND. Кілька правил дають об'єднання результатів без повторних карток у спільній добірці.
- Категорії: музика/концерти, фієсти/фестивалі, спорт, кіно, театр/вистави, виставки/культура, сімейні події, ярмарки/їжа, навчання/майстер-класи, бізнес, інше. Підкатегорії можна додавати без зміни схеми.
- Список, карта, картка події, збереження, джерело, дата останньої перевірки, зовнішнє посилання на організатора/квитки.
- Окремі мови інтерфейсу, перекладу описів та фільтра мови проведення. Інтерфейс: uk/en/es. Переклад: мовні коди з перевіреного списку постачальника, спочатку щонайменше uk/en/es. Мова події може бути невідомою.
- Незалежні налаштування частоти доставки та періоду подій: щодня, вибрані дні тижня, кожні N днів; майбутні N днів/місяців, вихідні або явний діапазон дат. Час відправлення й часовий пояс задає користувач.
- Push, історія добірок усередині апки, тихі години, пауза правил, нагадування для збережених подій.
- Повторювані події/сеанси як окремі occurrences. Серія або фестиваль може об'єднувати кілька occurrences.
- Повідомлення про зміну/скасування збереженої події, якщо джерело надало відповідне оновлення.
- Мінімальна монетизація Free / Plus, магазинні підписки й відновлення покупок.
- Адмінка для джерел, помилок імпорту, подій, категоризації та ручних виправлень.
- Щонайменше три перевірені реальні джерела, із них одне у другій країні; користувацьке покриття позначене явно. Демо-дані окремо від реальних.

Міжнародність означає глобальну модель територій, мов і часових поясів. Вона не означає обіцянку повної афіші всіх країн. Вибір непідключеної території доступний, але апка показує, що джерел поки немає.

Пізніше: довільне малювання пальцем, email/Telegram/WhatsApp, власний продаж квитків, чати, соціальний граф, кабінет організатора, поведінкові рекомендації, маршрути, OCR афіш, масовий імпорт кіносеансів через платний фід.

Кіно є категорією в MVP, але реальні сеанси показуються лише після підключення відповідного джерела. Каталог фільмів не замінює кіносеанси. Спорт розділяє участь і перегляд. Порожнє покриття категорії не маскується вигаданими даними.

Ці оцінки не є аудитом коду. Не вважати README «production-ready» доказом. Фіксувати commit SHA, ліцензію, реальні залежності, результат запуску та запозичені частини. Дати активності брати з Git, не з дати індексації пошуковиком.

Не зливати цілі репозиторії без перевірки. Обрати одну мобільну основу. З community-calendar брати лише потрібний процес збору та моделі; особисті інтеграції автора й містоспецифічний UI не є вимогами продукту. Зберігати LICENSE/NOTICE та перелік запозичень. Умови на код не надають прав на події, описи й зображення сторонніх джерел.

## 4. Початкова архітектура

Рекомендований напрям; S0 може скоригувати його за фактичними результатами:
- apps/mobile: Expo / React Native / TypeScript.
- apps/admin: невелика вебадмінка (наприклад Next.js).
- services/ingestion: Python worker, якщо повторно використовуємо Python pipeline community-calendar. Не переписувати робочі модулі на Node тільки заради однієї мови.
- supabase: PostgreSQL / PostGIS, Auth, міграції, RLS, мінімальні Edge Functions.
- notifications: серверний планувальник, durable jobs у PostgreSQL, Expo Push. Cron — лише тригер для worker, а не єдине сховище стану.
- billing: RevenueCat поверх App Store / Google Play; серверні entitlements.
- AI: один фактичний постачальник за адаптером, structured output, ліміти витрат і кеш. Не підключати кілька провайдерів без потреби.
- maps/geocoding: MapLibre і окремо обрані постачальники тайлів, геокодингу та адміністративних меж. Демосервери не використовувати як production-інфраструктуру.

Схема обміну: джерело → worker → нормалізовані події в базі → відбір за правилами → збережена добірка → push із deep link.

GitHub Actions може бути тригером обмеженого імпорту. Не покладатися на нього для точної доставки сповіщень за графіком. Один worker / база на старті; Redis, Kafka й мікросервіси лише за виміряної потреби.

## 5. Дані й інваріанти

Мінімальні сутності (допускається об'єднання таблиць із поясненням):
- profiles: locale, translation_locale, notification_timezone.
- territories: ISO country, зовнішній стабільний ідентифікатор, назва, адміністративна ієрархія, геометрія/центр, походження меж.
- rules і rule_areas: власник, enabled, категорії, фільтри, тип території (country/admin/city/radius/polygon), параметри часу, графік, timezone, next_run_at.
- sources: URL/API, території, категорії, спосіб отримання, статус умов використання, частота, last_success_at, дозволи на кеш/переклад/зображення.
- source_records: provider + external_id, payload hash, fetched_at, посилання; зберігання сирих даних відповідно до дозволів.
- events і occurrences: canonical id, parent/series id, назва, категорії, оригінальна мова, мова проведення, status, venue/location, геометрія, start/end, timezone, дата без часу, ціна/валюта або unknown.
- event_sources: provenance і зв'язок із записами джерел.
- translations: event/version/locale/provider, статус і переклад.
- saved_events, device_tokens, digests, digest_items, notification_jobs/deliveries, entitlements, ingestion_runs.

Обов'язкові правила:
- UTC timestamps для відомого часу, IANA timezone для локальної інтерпретації; зберігати date-only як date-only. Не вигадувати 00:00, ціну 0, координати або мову.
- Одна occurrence може мати кілька джерел. Різні сеанси не склеювати через однакову назву.
- Повторний імпорт не створює нової події; повторне завдання не створює нової добірки.
- Пропажа зі стрічки не дорівнює скасуванню. Скасування потребує явного сигналу або ручної перевірки.
- Геопошук із PostGIS та індексами; зміст country/admin фільтрів не підмінювати радіусом від центру країни.
- Валідний полігон на старті: 3–100 вершин, без самоперетину; зони через антимеридіан коректно обробляти або явно відхиляти з поясненням у MVP.
- Приватні дані доступні лише власнику; server-only ключі не потрапляють у mobile bundle.
- Опис не використовується як інструкція для AI. Результат AI проходить schema validation; дати й адреси звіряються з джерелом.
- Подія завжди має provenance, перевірку актуальності й відкриття оригіналу.

## 6. Політика сповіщень

Графік відправлення та горизонт подій зберігати окремо. Daily о 18:00 означає місцеві 18:00 у вибраному IANA timezone, а не UTC + фіксований offset. Every N days — N календарних днів від anchor date у тому ж timezone.

Для DST визначити й протестувати політику: неіснуючий локальний час переносити на наступний доступний; повторений локальний час виконувати один раз. Якщо користувач змінює timezone або графік, next_run перераховується.

Добірка показує всі актуальні відповідні події у вибраному періоді, групує за правилами й датами, прибирає дублікати. Push відправляється, коли є нові/змінені відповідні події; повтор старих без змін можна вмикати налаштуванням. Нова добірка доступна в апці незалежно від push.

MVP не обіцяє справжній real-time: окреме сповіщення про нову подію/зміну надсилається після успішного імпорту. Показувати дату перевірки й фактичну частоту джерела.

Тихі години, pause й opt-out діють серверно. Один device token належить поточному користувачу; logout прибирає прив'язку. Не дублювати перетини правил. Кілька нагадувань для збереженої події (наприклад 1 день/2 години) створюються лише для відомого часу; зміна дати переплановує їх.

Для jobs потрібні lease/claim, retries із backoff, ідемпотентний business key, журнал результату, обмеження частоти й обробка недійсних device tokens. Push може доставлятися із затримкою чи повторно на стороні транспорту; не обіцяти exactly-once delivery. Гарантувати одну логічну добірку, дедуплікацію jobs й обережні повторні спроби при невизначеному статусі.

## 7. Монетизація

Цінова гіпотеза: Plus €4.99/місяць або €39.99/рік. Фактичні ціни, валюти й trial визначаються продуктами магазинів, не hardcoded рядком у UI.

Free: 1 активне правило, місто/радіус, щотижнева добірка, основний перегляд, базовий переклад, збереження.
Plus: до 10 активних правил, країни/регіони/полігони, власні графіки й додаткові фільтри. Країни доступні для перегляду всім; paywall стосується активного моніторингу.

Скасування збереженої події — безкоштовно. Модель entitlements перевіряється серверно. Після закінчення Plus події та правила зберігаються; зайві правила paused, користувач може вибрати одне Free-правило. Реалізувати restore, expiry, grace period, повторні та невпорядковані webhooks. Якщо webhook не дає надійного поточного стану, запитати його у провайдера; не довіряти одному клієнтському прапорцю.

## 8. Етапи реалізації

### S0 — Перевірити основи й зафіксувати рішення
Завдання: прочитати чинні інструкції workspace; перевірити кандидатів, licenses, commit SHA, package manifests, історію й залежності; запустити базові перевірки двох основних кандидатів у тимчасових checkouts; оцінити iOS/Android; вибрати спосіб повторного використання. Інвентаризувати зовнішні акаунти/ключі й джерела.
Результат: docs/REPO_AUDIT.md, docs/ARCHITECTURE.md, docs/SOURCES.md, docs/SETUP.md, docs/PROGRESS.md. Для кожної основи: use/adapt/reject із причиною. Невиконаний native build позначити unverified, не pass.
Готово: є фактична перевірка коду, один обраний mobile starter, визначений ingestion підхід і перелік блокерів. Не починати весь MVP у цьому етапі.

### S1 — Створити основу й середовище
Завдання: імпортувати обрану основу в власний репозиторій зі збереженням attribution, налаштувати mobile, мінімальну структуру worker/admin, env examples, lockfiles, локальний запуск, development/staging configs, CI перевірки.
Готово: стартовий екран запускається; перевірки коду працюють; немає secret у tracked файлах; є точні команди та список неперевірених native платформ. Не створювати порожні сервіси для майбутніх функцій.

### S2 — База, авторизація й приватність
Завдання: міграції, PostGIS, основні таблиці, індекси, RLS, email auth, reset, session persistence, logout, account deletion. UI uk/en/es. Імпорт дозволених територій/демо-територій із походженням даних.
Готово: база створюється з нуля; користувач A не читає/не змінює приватні записи B; logout/relaunch працюють; видалення прибирає приватні дані, не публічні події. Дані перекладу інтерфейсу повні.

### S3 — Перший наскрізний сценарій на реальному джерелі
Завдання: один погоджений ICS/API/HTML source adapter → нормалізація → база → просте правило міста/категорії → картка в mobile → збережена добірка → development push на фізичний пристрій. Показати джерело й last_checked.
Готово: повторний імпорт не створює дублікати; одна реальна подія проходить увесь процес. Без зовнішніх ключів допускається локальний transport fixture, але real push залишається blocked до фактичної доставки. Не називати fixture реальною інтеграцією.

### S4 — Території, полігони й правила
Завдання: вибір кількох країн/регіонів/міст, радіус, полігон точками, CRUD/пауза правил, категорії, бюджет/валюта, мова події, age range якщо відомий, діапазони дат. Ввести «невідомі значення допускаються/виключаються» для мовних/цінових фільтрів. Валідувати геометрію серверно.
Готово: перевірені точки всередині/на межі/поза зоною, admin boundaries, перетини правил, невідомі координати/ціна/мова, country OR і category OR. Валюти не порівнюються між собою без конвертації; MVP використовує явний currency filter.

### S5 — Мобільний досвід
Завдання: короткий онбординг (території → інтереси → графік → preview), feed/map/detail/saved/rules/inbox/settings. Search, pagination, marker clustering за потреби, empty/loading/error states, permission fallback, accessibility, deep links.
Готово: користувач налаштовує правило без GPS; бачить відповідні події й покриття; відкриває карту/джерело, зберігає подію; UX перевірений на iOS та Android. Фінальний дизайн перевірити в обох світлій/темній темах, якщо обидві пропонуються.

### S6 — Більше джерел, якість і AI
Завдання: щонайменше 3 реальні джерела у 2 країнах, source registry, bounded polling, event updates, safe dedup/review, категоризація, переклад і короткі описи. Обирати модель через конфігурацію й актуальний доступ, не вигадувати model id. Кеш за version/locale, budget caps, source-specific TTL, backoff, metrics.
Готово: fixtures перевіряють extraction; якість вручну звірена із джерелами; різні сеанси не склеєні; повтор не витрачає AI знову без зміни; AI outage не зупиняє базовий feed. Не подавати непідтверджені мову/ціну як факти.

### S7 — Гнучкі регулярні добірки
Завдання: daily/selected weekdays/every N days, timezone, horizon/custom dates/weekends, quiet hours, pause, durable scheduler/jobs, збереження всіх digest items, короткий push і deep link. Послідовні retries і receipts.
Готово: перевірені DST для Europe/Madrid, інший timezone, перезапуск worker, два worker одночасно, зміна правила, відсутність нових подій, invalid token, перегляд історії без push permission. Повтор job не створює другу логічну добірку.

### S8 — Зміни, скасування й нагадування
Завдання: відстеження важливих полів, окремі зміни для saved events, lead-time reminders, перепланування, керування статусами outdated/unknown/cancelled, ручна корекція.
Готово: зміна початку переплановує нагадування; скасування зупиняє їх і створює одне логічне оновлення; зникнення із джерела не означає cancelled; date-only події обробляються без вигаданого точного часу.

### S9 — Free/Plus та магазинні покупки
Завдання: RevenueCat SDK, entitlements, серверні обмеження, products/offering, paywall, restore, authenticated webhooks, reconcile, expiry/downgrade.
Готово: sandbox покупка й restore реально перевірені на обох платформах; повтор webhook безпечний; прострочена підписка не видаляє користувацькі дані; користувач Free не обходить limits прямим API. За відсутності store setup етап blocked, не done.

### S10 — Адмінка та операційна надійність
Завдання: admin auth/roles, CRUD sources, status imports, ручна перевірка/merge, coverage dashboard, AI usage, job errors, аудит корекцій. Source overrides мають чітку політику збереження при повторному імпорті. Документувати backups, restore, retries й відключення джерела.
Готово: звичайний користувач не має admin доступу; видно падіння джерела й застарілі записи; адмін може виправити подію без її повторного псування імпортом. Перевірено відновлення бази у staging, а не лише наявність опису backup.

### S11 — Бета й перевірка всього сценарію
Завдання: integration/E2E smoke на iOS/Android, тестові користувачі, конфігурація staging worker, push і покупки, release builds, перевірка permission/deep links/background states. Виміряти час геозапиту на реалістичних synthetic даних; позначити ці дані synthetic. Зібрати мінімальні opt-in або належно налаштовані метрики: правило створено, добірка відкрита, подія збережена, перехід до організатора, покупка.
Готово: звіт docs/QA_REPORT.md із device/OS/build, пройденими перевірками й дефектами; немає критичних дефектів auth/billing/date/notifications; реальний сценарій повторений обома платформами. Невиконані перевірки явно listed.

### S12 — Підготувати реліз
Завдання: release configs, migrations/deploy runbook, signing prerequisites, store metadata/screenshots, privacy/data disclosures, account deletion, support/contact, billing disclosures, перевірка умов джерел. Політики використовують фактичні дані оператора й провайдерів; відсутні реквізити не вигадувати.
Готово: build artifacts для обох платформ, staging acceptance, актуальні setup/release docs, список залишених зовнішніх дій. Публікація/схвалення магазинами — окремий факт, не еквівалент наявності коду. Відсутні акаунти, ключі, тестувальники чи затвердження магазинів не замінювати mocks.

## 9. Як фіксувати прогрес

docs/PROGRESS.md містить таблицю S0–S12: pending / in_progress / implemented / verified / blocked. implemented означає код є; verified — усі критерії фактично перевірені. У blocked указувати виконану частину, конкретний блокер і наступну дію.

Для поточного етапу записувати: що змінилося, рішення/відхилення від плану, команди й результати, SHA локального checkpoint якщо створений, external prerequisites, наступний крок. Не комітити unrelated зміни користувача; не створювати push/remote без відповідного завдання. Зберігати роботу в git за правилами репозиторію.

docs/DECISIONS.md — короткі рішення з причинами. docs/SETUP.md — фактичні команди, версії runtime, env variable names без значень секретів, порядок запуску. docs/SOURCES.md — доказ прав/умов, географічне/категоріальне покриття та здоров'я джерел. docs/THIRD_PARTY.md — attribution і запозичені файли/модулі.

## 10. Зовнішні передумови

Codex має інвентаризувати наявне, а не припускати доступ:
- Доступ до workspace/git та мережі для кандидатів.
- Supabase project або локальне середовище; development/staging секрети.
- Expo project, push credentials, physical iPhone/Android або користувач, який може провести device checks.
- Apple / Google developer accounts, signing, store test setup і тестувальники за чинними вимогами.
- RevenueCat project, продукти/entitlements/offering, webhook secret.
- Один AI provider із ключем і встановленим budget; тариф не фіксувати з пам'яті.
- Map tiles/geocoder/boundaries, їх ключі й дозволи.
- Перевірені джерела з можливістю повторного використання даних, дозволами на переклад/кешування.
- Дані оператора продукту, support contact та остаточне рішення щодо бренду.

Не зупиняти незалежну реалізацію через один відсутній ключ. Використовувати явно позначені fixtures для development, але залишати зовнішній критерій blocked до перевірки. Запитувати лише відомості, що блокують конкретну дію; не вимагати всі акаунти на S0.

## 11. Визначення готового MVP

MVP verified лише коли користувач на iOS й Android може:
1. Увійти, налаштувати мову, створити кілька правил у межах тарифу.
2. Обрати міста/країни/регіони/радіус/полігон, категорії й часові фільтри.
3. Отримати реальні події з джерел, побачити покриття, переклад, оригінал і актуальність.
4. Зберегти подію, отримати добірку за графіком і відкрити її з push.
5. Отримати відоме оновлення/скасування й налаштоване нагадування.
6. Купити/відновити Plus у sandbox, а backend коректно обмежує Free/expiry.
7. Змінити правила, вимкнути push, вийти й видалити акаунт.

Водночас адмін контролює джерела та помилки, імпорт і планувальник відновлюються після перезапуску, усі required перевірки мають докази. «Готово до бети», «готові release builds» та «опубліковано в магазинах» — різні статуси.
