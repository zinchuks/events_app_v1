# Правила Event Radar

## Обов’язкова передача роботи між AI

- На початку кожної сесії прочитати [docs/HANDOFF.md](docs/HANDOFF.md), останні записи [docs/WORK_LOG.md](docs/WORK_LOG.md), [docs/PROGRESS.md](docs/PROGRESS.md), [MVP_PLAN.md](MVP_PLAN.md) і [CODEX_PROMPTS.md](CODEX_PROMPTS.md); для архітектурних змін — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Перевірити `git status --short` і `git log -5 --oneline`. Не починати проєкт заново й не покладатися на історію чату як єдине джерело стану.
- `HANDOFF.md` — одна актуальна точка відновлення: поточне завдання й дозволений обсяг, останній реалізований результат, точний крок зупинки, незавершені зміни/файли, перевірки, блокери та перша наступна дія. `PROGRESS.md` — статуси S0–S12 і докази. `WORK_LOG.md` — хронологічний журнал; додавати записи, не стирати попередню історію. Не копіювати весь журнал у handoff.
- Перед змінами коротко записати нове завдання та стартовий commit у журнал, а в handoff позначити `in_progress`. Після кожної суттєвої частини роботи, зміни напрямку чи виявлення блокера записувати, що змінилося, і пересувати точку зупинки. Перед завершенням відповіді, передачею іншому AI або запланованим очищенням контексту обов’язково оновити handoff, журнал і потрібні статуси прогресу. Це стосується також частково виконаної роботи та змін лише в документації.
- Кожний запис: дата/час із часовим поясом, запит/етап, змінені файли й поведінка, фактичні команди та результати перевірок або «не виконано» з причиною, точний крок зупинки, блокери, наступна дія, Git checkpoint або явний стан незакомічених змін. Якщо консультація впливає на подальшу розробку, також одразу записати її результат і позначити «продуктовий код не змінювався».
- Не називати всю розробку завершеною через завершення одного завдання. Розрізняти `implemented`, `verified`, `blocked`, `pending`; старі докази вказувати з датою, не видавати їх за повторний запуск. Рекомендований наступний крок не є дозволом виконувати його. Актуальний запит користувача визначає обсяг; відмінність від handoff записати.
- Якщо handoff застарів або суперечить коду/Git, перевірити факти та виправити запис до залежної роботи. Не записувати секрети, паролі, токени чи особисті дані в журналах; для доступів зазначати лише назву необхідної конфігурації. Не заявляти заздалегідь SHA майбутнього commit: записати наявний checkpoint, для поточного документаційного commit послатися на `git log -1`.
